# 콘텐츠 작성·검증 운영 기준

이 문서는 연마의 도구 설명, 가이드와 아티클을 작성·수정할 때 사용하는 내부 기준이다. 공개 소개 페이지에는 방문자가 판단에 필요한 운영 주체, 제공 범위, 이용 한계와 문의 방법만 표시하고 상세 작업 절차는 공개하지 않는다.

## 공개 정보의 범위

- 공개 글의 작성 주체는 `HPMPLab`으로 통일한다.
- 가이드에는 최종 검증일, 확인한 기능 범위와 전문 검수 여부를 표시한다.
- 아티클에는 카테고리, 발행일과 사실·의견의 성격을 구분해 표시한다.
- 본문 분량을 바탕으로 추정한 읽기 시간(`약 N분`)은 독자에게 표시하지 않는다.
- 외부 자료를 사용하면 자료가 무엇을 보여 주고 현재 주장에 어떤 의미가 있는지 먼저 설명한 뒤, 해당 설명 가까이 원문 링크를 둔다. 링크 자체가 설명을 대신하게 하지 않는다.
- 건강·운동·측정·확률 정보에는 적용 한계와 중단 조건을 함께 안내한다.
- 오류 제보와 정정 요청은 공개 문의 페이지로 연결한다.

## 작성과 검증 절차

1. **구현 대조:** 시간, 단위, 계산식, 저장 범위와 지원 조건을 실제 HTML·JavaScript 구현과 대조한다.
2. **근거 구분:** 외부 연구나 공식 문서에서 확인한 사실, 앱이 선택한 기본값, 기기 제약에서 추론한 값을 구분한다.
3. **실패 조건 확인:** 정상 흐름뿐 아니라 권한 거부, 샘플 부족, 파일 형식 오류와 연결 중단 조건을 확인한다.
4. **화면 확인:** 데스크톱과 모바일에서 주요 콘텐츠, 키보드 포커스, 오류 상태, 내부 링크와 가로 넘침을 점검한다.
5. **문서 동기화:** 공개 기능이 바뀌면 관련 가이드와 `docs/현재작업중.md`를 함께 갱신한다. 검증일은 실제 재검증이 있었을 때만 바꾼다.
6. **실배포 확인:** 배포 작업 성공 여부와 `hpmplab.com`이 최신 HTML·자산을 제공하는지 별도로 확인한다.

## 완성 원고 모드

- 공개 글을 쓰는 단계에서는 분석 과정을 설명하는 조수가 아니라 독자에게 바로 공개할 작가로 행동한다.
- 최신 자료가 필요한 글은 `취재 → 집필 → 퇴고`를 분리한다. 취재 단계에는 검증된 사실, 논쟁점, 장면 후보, 반론과 중심 명제 후보만 남기고 독자용 서론이나 결론을 만들지 않는다.
- 집필 단계는 취재 노트에서 하나의 중심 논지를 고르고 장면·문제·주장 중 하나로 바로 시작한다. 자연스러운 칼럼·에세이 초고는 Terra Medium, 문장 밀도와 구조가 더 필요하면 Sol Medium을 우선한다.
- 퇴고 단계는 기존 원고에 새 사실을 추가하지 않는다. 작성 과정, 구조 안내, 불필요한 양비론, 반복 유보, 중복 결론과 관성적인 접속어를 제거하고 완성 원고만 남긴다.
- 원고에는 제목과 완성 본문만 둔다. 계획, 접근 방법, 선택 이유, 자기평가, 예상 독자 반응, 작성 포인트와 후속 질문은 내부 작업 문서에만 남긴다.
- `다음과 같이 작성했다`, `이 글에서는`, `먼저 살펴보자`, `핵심은 다음과 같다`, `균형 있게 보자면` 같은 작업 안내를 공개 본문에 쓰지 않는다.
- 주장을 분명히 쓰되 과장하지 않는다. 실제로 중요한 불확실성만 정확히 한정하며, 한 문단의 유보 표현은 꼭 필요한 경우 한 번으로 제한한다.
- 여러 관점을 나열하는 데 그치지 않고 근거를 충돌시켜 하나의 판단으로 수렴시킨다. 같은 결론을 도입·본문·결론에서 반복하지 않는다.
- 문단마다 중심 생각 하나를 전개하고, 추상적인 평가보다 구체적인 장면·행동·사례·원인과 결과를 앞세운다.
- 문체는 단정적이되 과장하지 않고, 지적이되 논문처럼 건조하지 않은 현대 한국어를 사용한다. 감정은 장면과 문장 리듬으로 드러내고 직접 해설하지 않는다.

## 독자를 위한 문장과 서사

- 첫 문단은 글마다 독자가 겪을 만한 장면, 당장 풀어야 할 문제 또는 중심 판단 중 가장 적합한 하나로 시작한다. 질문형 제목도 고정된 도입 순서를 따르지 않는다.
- 독자가 용어와 논쟁을 이미 안다고 가정하지 않는다. 다만 정의와 유행 배경은 도입의 의무 절차가 아니라, 독자가 장면·문제·판단을 이해하는 데 필요한 위치에 자연스럽게 넣는다.
- 도입에는 글을 어떻게 검증하고 전개할지 안내하지 않는다. 핵심 질문에 대한 잠정적인 답이나 서로 충돌하는 판단을 남겨 본문을 읽을 이유를 만든다.
- 중심 사례를 도입에서 사용할 수도, 첫 본문 절에서 구체화할 수도 있다. 어느 쪽이든 같은 장면과 결론을 도입과 첫 절에서 되풀이하지 않는다.
- 한 문단에서는 한 가지 질문만 답한다. 첫 문장은 문제를 열고 마지막 문장은 다음 문단이 필요한 이유를 잇는다.
- 같은 개념은 글 전체에서 같은 이름으로 부른다. 새로운 분류를 추가해야 한다면 기존 분류와의 관계부터 설명한다.
- 글 전체를 관통하는 사례 하나를 정하고, 목표·행동·기록처럼 개념이 확장될 때도 같은 사례를 이어서 사용한다. 실제 인물이나 사건이 아닌 가상·구성 사례는 첫 등장 문장에서 그 성격을 명시한다.
- 연구는 독자가 알아야 할 결론을 먼저 말한 뒤, 무엇을 비교했는지와 판단에 필요한 수치만 설명한다. 연구 방법과 숫자가 문단의 첫 박자를 차지하지 않게 한다.
- 차트의 라벨 위치, 이미지 생성 방식, 후보 점수와 작업 순서 같은 제작 메모를 독자용 본문에 쓰지 않는다. 차트가 보여주는 시장 의미만 설명한다.
- 공개 대시보드의 소개문·도움말·카드 문구도 독자가 읽는 본문으로 취급한다. `같은 데이터로 연결한다`, `기준 시각을 표시한다`, `추천 대신 조건을 보여준다`처럼 기능 설계와 편집 원칙을 설명하지 말고, 최신 시장에서 확인된 사실과 독자가 판단할 의미를 바로 쓴다.
- 공개 글은 완성된 사실과 해석을 전달하는 글이지 조사 일지가 아니다. `확인했다`, `찾아봤다`, `확인되지 않았다`, `추정하지 않았다`, `공지와 보도를 검토했다`, `오늘 이슈로 재사용하지 않는다`처럼 작성자의 취재·검색·검증·선별 과정을 설명하는 문장은 내부 보고서와 상태 문서에만 남긴다.
- 발생하지 않은 사건은 기본적으로 쓰지 않는다. 사이드카·서킷브레이커·공급계약·청산 등은 실제 발생이 확인되고 독자의 시장 판단에 영향을 줄 때만 공개 본문에 포함한다.
- 소문 자체가 가격을 움직여 언급할 필요가 있으면 확인된 사실과 시장 영향만 쓴다. 무엇을 검색했고 무엇을 배제했는지는 독자에게 설명하지 않는다.
- 목록과 표는 항목을 비교하거나 실제로 실행할 때만 사용한다. 목록을 연속해서 배치하지 않고, 목록 뒤에는 독자가 무엇을 선택할지 설명한다.
- `HC-###`, 작성 큐, 내부 자료팩 같은 편집 정보는 공개 본문에 노출하지 않는다. 글의 끝에는 이번 글의 결론, 지금 해볼 행동과 실제로 공개된 다음 읽을거리 하나만 둔다. 결론·FAQ·안전 고지에 같은 판단이나 주의 문구를 반복하지 않고, 각각 가장 필요한 한 곳에만 둔다.
- 초안은 소리 내어 읽어 주어·행동·결론이 한 번에 잡히는지 확인한다. 뜻을 이해하려고 앞 문장을 다시 읽어야 하면 추상명사를 동사와 구체적인 장면으로 바꾼다.
- 글이 던진 핵심 질문에는 늦어도 도입 세 문단 안에서 먼저 답한다. 배경 설명과 용어 정의는 그 답을 이해하는 데 필요한 순서로만 붙인다.
- 건강정보 글은 기본적으로 의미 있는 본문 절 5~6개로 구성한다. 모든 절은 앞 절에서 생긴 질문에 답하고 다음 질문을 열어야 하며, 같은 결론을 다른 연구로 반복하지 않는다.
- 문단은 대체로 2~4문장으로 쓰되 길이를 기계적으로 맞추지 않는다. 한 문단이 한 장면, 한 결론 또는 한 행동만 맡도록 나눈다.
- 연구가 사례를 밀어내지 않게 한다. 중심 인물이 겪는 다음 문제를 먼저 보여 주고, 한 절에는 판단에 가장 중요한 연구 하나와 결론을 바꾸는 숫자 하나만 우선 배치한다.
- 글의 절반이 지나기 전에 독자가 바로 써 볼 문장이나 행동을 제시한다. 연구 설명은 그 실천이 왜 타당한지 확인하는 역할을 맡는다.

## 자동화 도구 사용

- 코드·문서 초안, 반복 검사와 형식 정리에 자동화 도구를 사용할 수 있다.
- 자동화 결과를 사실로 바로 게시하지 않고 실제 코드, 브라우저 동작과 인용 원문을 대조한다.
- 직접 측정하지 않은 효과나 사용 경험을 측정한 것처럼 서술하지 않는다.
- 자동 생성 여부보다 게시된 내용의 정확성, 고유한 편집 가치와 검증 가능한 근거를 우선한다.

## 시황 대표 이미지

- 시황 썸네일은 이전 이미지의 분위기나 소재를 생성 기준으로 삼지 않는다. 당일 리서치에서 중요도가 가장 높은 사건 1~2개로 새 시각 논제를 만든다.
- 생성 전에 `주도 사건`, `시장 방향`, `독자에게 남길 감정`, `색과 빛`을 정한다. 제목·도입부·대표 이미지가 같은 사건을 말해야 한다.
- 약세장도 검정·차콜 배경과 붉은 하락 화살표를 관성적으로 반복하지 않는다. 공급 부족, 포지션 이동, 정책 변화, 반등 조건 등 그날만의 구조를 밝은 자연광과 선명한 대비로 표현할 수 있다.
- 밝은 아이보리·하늘색·청록·금색·산호색 등 색 범위를 넓히고, 실제 긴급 충격이 핵심일 때만 어두운 톤을 제한적으로 사용한다.
- 글자, 숫자, 로고와 워터마크는 넣지 않는다. 1200×630 가로형으로 만들고 모바일 중앙 크롭에서도 핵심 피사체가 남아야 한다.
- 이전 대표 이미지는 생성 참조로 넣지 않는다. 게시 전 목록 화면에서 소재·구도·주조색이 최근 글과 겹치는지만 확인한다.
- 이미지 설명은 독자가 시황의 핵심 사건을 이해하도록 작성하며 생성 방식, 배치 지시, 라벨 처리 같은 내부 편집 메모를 쓰지 않는다.

## 안전과 표현

- `A가 아니라 B다` 식의 대조형 부정 문장을 문단마다 되풀이하지 않는다. 사실은 먼저 직접 문장으로 쓰고, 해석의 범위와 이용 한계는 글 상단 고지와 해당 주장 가까이에 한 번만 둔다.
- 연마는 의료기관, 전문 코칭 기관, 복권 판매·예측 서비스가 아니다.
- 전문 자격자의 검토를 받지 않은 글은 이를 암시하지 않는다.
- 의료 진단·치료 효과, 수익, 당첨이나 측정 정확도를 보장하지 않는다.
- 논문 조건과 앱 구현이 다르면 동일한 프로토콜이라고 표현하지 않는다.
- 호흡·숨참기·손가락 로딩처럼 안전과 관련된 글에는 통증, 어지러움과 비정상적인 불편이 있을 때의 중단 안내를 둔다.
- 로또 관련 글은 모든 유효 조합의 당첨 확률이 같으며 과거 빈도나 앱 점수가 다음 회차를 예측하지 못한다는 점을 명시한다.

## 정정

재현 가능한 오류는 원인이 확인된 뒤 코드와 관련 문서를 함께 수정한다. 화면, 브라우저, 입력값과 재현 순서가 있으면 우선 확인하며, 개인의 부상 진단·의료 판단·제품 구매 보증과 당첨 번호 상담은 답변 범위에 포함하지 않는다.
